# 发布下一批课程

## 扩展已有课程

以 `dont` 课程新增 `dont-11` 为例：

1. 复制 `public/courses/dont.2.0.0.json` 为 `dont.2.1.0.json`。
2. 把包的 `version` 改为 `2.1.0`，保留课程 ID `dont`、原 10 题及其 ID，在 `sentences` 末尾追加新题。
3. 计算新文件的 SHA-256：

   ```sh
   node scripts/hash.mjs public/courses/dont.2.1.0.json
   ```

4. 在 `public/manifest.json` 中仅替换该课程条目的 `version`、`url`、`sha256`。其他课程条目继续保留。
5. 更新清单顶层 `version`、`updatedAt`、`releaseNotes`。
6. 执行验证和构建：

   ```sh
   npm test
   npm run build
   ```

7. 将新课程文件和新清单放在同一个 Git 提交后推送。Cloudflare Pages 构建成功后发布的是完整静态目录，避免清单先上线而课程文件尚不存在。
8. 在已练习过的固定生产网址进入“设置 → 检查更新”，确认新课程版本、句数和原题进度均正确，再断网重新打开测试。

课程文件使用版本化文件名，发布后不原地改写历史文件。更改任何字节后都要重新生成摘要；最好写入一个新版本文件。SHA-256 用于发现缓存错配、截断和损坏，不代替 HTTPS 信任。

## 新增一个句型课程

新建 `public/courses/used-to.1.0.0.json`，设置唯一课程 ID `used-to`，为题目分配 `used-to-01` 等全局唯一 ID。计算摘要后，在清单 `courses` 数组中追加完整条目并更新清单版本、日期和发布说明，其余步骤相同。

同 ID 的旧题保留进度；新题从未学习开始。当天已经完成 20 题的用户收到更新后，仍须次日才能继续计分，不会因为题库更新绕过每日上限。

## 更新初始题库

常规课程发布无需更新 `builtin-v2.json`；首次联网会先使用这份可靠的初始库，然后自动更新。长期维护时，可把最新完整清单和全部课程打包为新的初始库；其格式仍为 `{ "manifest": 完整清单, "courses": 全部课程对象数组 }`。

如果替换或重命名初始库，需同步修改 `app.js` 首次加载地址、`sw.js` 的预缓存列表和 `scripts/validate.mjs` 的路径，并按程序升级流程递增 SW 版本。保留历史课程文件。

## 程序升级

当 HTML、CSS、JS、图标、安装清单或初始库发生变化时：

1. 修改程序文件。
2. 递增 `public/sw.js` 的 `APP_VERSION`，例如 `3.0.1`。同时更新 `package.json` 版本和设置页程序版本文字。
3. 如果新增、改名或删除静态文件，更新 SW 的 `ASSETS` 列表。课程独立版本文件不必逐个列入，应用校验后会写课程缓存。
4. 运行测试和构建，提交并推送。
5. 验证已安装的旧程序出现“新版本已准备好”，点击“重新加载”后切换，学习记录和课程目录保持不变。

不要只改 CSS / JS 而不改 SW 版本；否则旧版本缓存会继续被使用。不要自动调用 `skipWaiting()` 或强制刷新用户正在作答的页面。

程序安装时会完整预缓存全部必需文件；失败则不激活。课程更新与程序更新独立，课程发布不需要递增 SW 版本。

## 更新失败处理

- 404：检查文件路径、大小写、是否提交和构建成功。
- SHA 校验失败：对实际发布字节重新计算摘要，检查编辑器换行变化和错误缓存规则。
- JSON / ID 错误：先运行 `npm run validate`。
- 存储不足：先导出进度，释放设备空间后再检查更新；失败期间继续用旧课程。
- 离线：继续练习本地课程，恢复联网自动再检查。

每次网络请求最长等待 12 秒。若清单含多课，逐课请求可能需要更长总时间；旧课程在后台下载期间仍可练习。
